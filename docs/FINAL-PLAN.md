# cover-pipeline 最终方案 v2

> 取代 `PLAN.md`。核心变化：从「一条命令的翻唱脚本」升级成「**带引导层、资源看板、配方库、开放接口的桌面级工具**」。
> 目标用户仍然是小白：不会选模型、不会调参、不知道自己要什么，但想快点听到成品。

---

## 一、用户旅程（小白视角）

```
装好 → 打开界面 → 体检（自动） → 回答 3~5 个问题 → 拿到 2~3 张方案卡
   → 选一张 → 一键配置环境（进度可见） → 建音色（训练或选现成）
   → 丢一首歌 → 出成品 → 不满意 → 界面告诉他「可能是接缝问题，试试这两个方案」
   → 选一个 → 再听 → 满意 → 存进曲库
```

每一步都能在界面上看到：花了多少时间、占了多少显存和磁盘、下一步该干什么。
命令行始终等价可用（`cover` 全功能），界面只是壳。

---

## 二、三层「方案」体系（这是本方案的核心）

小白口中的「方案」其实混了三件事，必须拆开，否则会做成四不像：

| 层 | 名字 | 回答什么问题 | 存放位置 | 谁维护 |
|---|---|---|---|---|
| L1 | **配置方案 plan** | 我这台电脑该用哪套模型和参数？ | `plans/*.yaml` | 官方维护，按显存档位分 |
| L2 | **配方 recipe** | 效果不对时，有哪些已知解法？ | `recipes/*.yaml` | 官方 + 社区提交 |
| L3 | **资源库 library** | 我有哪些模型、素材、音源、成品？ | SQLite 索引 | 用户自己的数据 |

对应三个命令：`cover plan`、`cover fix`、`cover lib`。

## 三、L1 配置方案：`cover plan`

### 3.1 探测（自动，不问用户）

- GPU：型号、显存、算力、CUDA 可用性
- 内存总量 / 可用
- 磁盘：各盘剩余空间、项目所在盘
- CPU 核数、Python 版本、ffmpeg 版本
- 已有依赖：`audio-separator`、`rvc-python`、`torch` 版本
- 已装模型与素材（走 L3 索引）

### 3.2 问卷（3~5 题，全部单选，可跳过用默认）

1. 你最在意什么？`音质优先 / 速度快 / 省空间 / 稳定不折腾`
2. 你会自己训练音色吗？`会 / 只想要现成模型 / 不确定`
3. 大概多久用一次？`偶尔 / 每周几次 / 每天`
4. 磁盘能给出多少空间？`10G / 30G / 100G+`
5. 能接受单曲等多久？`1 分钟 / 5 分钟 / 半小时也行`

### 3.3 方案库（`plans/*.yaml`）

每个方案是一份完整参数快照 + 一句人话解释 + 预估指标：

```yaml
id: vram8_quality
name: "8G 显存 · 音质优先"
for:
  min_vram_gb: 8
  max_vram_gb: 16
  prefers: [quality, stability]
separate:
  backend: uvr
  model: UVR-MDXC-Inst_HQ_4        # 质量好，慢
convert:
  backend: rvc                      # 生态最成熟，显存友好
  f0_method: rmvpe
  index_rate: 0.85
  protect: 0.4
estimate:
  per_song_minutes: 4
  vram_peak_gb: 6.8
  disk_per_song_mb: 240
  train_minutes_80ep: 50
explain: "分离用 HQ 模型，慢一点但伴奏干净；转换用 RVC 最稳，显存 6.8G 左右。"
```

### 3.4 推荐逻辑

打分而不是硬规则：`score = 满足硬约束(显存/磁盘) × 场景偏好权重 × 稳定性系数`。
输出 2~3 张卡片，每张写明：预计单曲耗时、显存峰值、每首歌磁盘占用、训练耗时、和另一张的差别（一句话）。
选完写进 `configs/local.yaml`，并跑一次 `cover doctor` 校验，失败就回退到上一个可用方案。

### 3.5 关于 RVC vs SVC（必须给结论）

| | RVC | SVC（so-vits-svc / diffusion-svc） |
|---|---|---|
| 生态 | 模型多、教程多、坑都被踩过 | 分散，版本兼容差 |
| 显存 | 8G 训练够用 | 训练吃 12G+ |
| 推理速度 | 快（20~40 秒/首） | 慢（diffusion 更慢） |
| 音质上限 | 中上 | 高 |
| 小白成功率 | 高 | 低 |

**结论：默认 RVC；SVC 放进「进阶」页签，标注「需要 12G 显存，成功率较低」，不作为默认路径。**
分离同理：默认 MDX-NET 系（快、稳），RoFormer 作为高质量可选项（显存换质量），Demucs 作为「要分轨」时的选项。

## 四、可视化界面

### 4.1 页面清单

| 页面 | 内容 |
|---|---|
| 首页 / 体检 | 硬件一屏概览、健康度评分、待办（缺依赖、缺模型） |
| 方案选择 | 2~3 张方案卡，可展开细节、可对比 |
| 环境配置 | 一键安装、实时日志、失败时给一条可执行建议 |
| 音色管理 | 训练向导、素材检查、已有模型列表 |
| 翻唱 | 丢文件 / 输歌名 → 进度条 → 试听 → 存库 |
| 问题诊断 | 听到问题 → 选症状 → 给 2~3 个配方 → A/B 试听 → 采纳 |
| 资源看板 | 显存、内存、磁盘实时曲线 + 占用明细（谁占的） |
| 库管理 | 模型 / 素材 / 音源 / 成品，四个页签，可搜索、可删除、可导出 |
| 设置 | 接口密钥、并发、缓存策略、清理规则 |

### 4.2 资源看板（他要的「直观感受到内存和储存占用」）

- **实时**：显存已用/总量、内存已用/可用、项目目录大小，5 秒刷新一次
- **预算**：跑之前先算「这首歌预计占 240MB」，跑完对比实际
- **配额**：可设上限（比如 30G），超了就提示清理，一键清 `1-源文件`/`2-人声` 保留成品
- **明细**：按目录、按歌曲、按模型分组，能点开看是哪些文件

### 4.3 技术选型

界面用 **FastAPI + 轻前端（HTMX/Alpine，单页）**，不用 gradio。
理由：要做实时曲线、库管理、A/B 试听、多页签，gradio 的布局和状态管理撑不住；FastAPI 还能顺便把 API 暴露给将来的客户端。
GPU 任务一律走后台任务队列（子进程 + 状态文件/SSE 推送），界面不阻塞。

## 五、L2 配方系统：`cover fix`（他举的接缝杂音就是典型）

### 5.1 结构

```yaml
id: seam_noise
symptom: "两段音频接缝处有咔哒声或杂音"
applies_to: [clip, full_segment]
recipes:
  - id: crossfade
    name: "交叉淡化 30ms"
    how: "在拼接点做等功率交叉淡化"
    cost: "极快，几乎不改音质"
    risk: "淡化过长会吃掉辅音"
    params: {fade_ms: 30}
  - id: warmup_model
    name: "预热模型（前 0.5s 空跑）"
    how: "转换前先喂一段静音，让模型进入稳态再处理正文"
    cost: "多花 1~2 秒"
    risk: "无"
    params: {warmup_seconds: 0.5}
  - id: overlap_align
    name: "重叠 + 相位对齐"
    how: "两段重叠 100ms，按相关性找最佳对齐点"
    cost: "慢一点"
    risk: "对齐失败时更糟"
    params: {overlap_ms: 100}
selected: warmup_model        # 这个案例的结论
evidence: "2026-10 实测：交叉淡化会吃掉尾音，预热模型完全消除接缝噪声，故选后者"
```

### 5.2 使用方式

- 命令行：`cover fix --symptom seam_noise --try crossfade,warmup_model` → 生成两版音频到 `work/<歌>/5-对比/`
- 界面：诊断页选症状 → 显示所有配方 → 一键生成对比 → 播放器左右切换 → 点「用这个」→ 写进 `decisions.jsonl` 并成为该症状的默认

### 5.3 决策记录

每次采纳写一条：`{symptom, candidates, chosen, at, 备注}`，存在 `D:\...\decisions.jsonl`。
作用：以后同类问题默认走上次选过的；也给社区贡献配方提供依据。

## 六、开放接口（`providers/`）

分三类，全部插件化，默认只实现本地，不内置任何第三方平台实现：

| 类型 | 接口 | 用途 | 默认实现 |
|---|---|---|---|
| `source` | `resolve(query) -> Path` | 拿到音频文件 | `local_file` |
| `publish` | `send(path, meta)` | 把成品发出去 | `local_folder`（拷到输出目录） |
| `ai` | `enhance(audio) / transcribe(audio) / denoise(audio)` | 接 AI 平台做增强、歌词、降噪 | `none`（不启用） |

配置里只留**占位和密钥字段**：

```yaml
providers:
  source: local_file
  publish: local_folder
  ai:
    enabled: false
    provider: ""            # 用户自己填
    api_key_env: ""         # 只读环境变量，不写明文进配置
```

原则：接口先留好、文档写清楚、示例写一个最小实现（`plugins/example_publish.py`），
具体接哪家由用户自己写，仓库不背第三方条款的锅。

## 九、风险与取舍

| 风险 | 应对 |
|---|---|
| 方案推荐不准，小白照做失败 | 方案卡上写死「预计耗时/显存」，选完立即 `doctor` 校验，失败自动回退 |
| 界面越做越重 | 界面只做壳，所有能力先有 CLI 等价命令 |

| 依赖版本地狱 | 转换/训练走「外部命令模板」，不硬绑某个库版本 |
| 磁盘被中间产物吃光 | 预算 + 配额 + 一键清理，默认只保留成品 |
| 版权与合规 | 不解密、不内置模型、不教绕过，见 DISCLAIMER |

## 十、已定事项（2026-11-05 维护者确认）

1. **默认后端 RVC，但由方案引擎决定具体参数**：RVC 是默认候选，不是硬编码。
   方案引擎按「显存 + 场景偏好 + 是否训练 + 磁盘 + 可等时长」在 RVC 的参数空间里选，
   只有用户显存 ≥12G 且明确选「音质优先」时，才把 SVC 作为并列候选并标注代价。
2. **配方要给利弊和推荐，不能只列选项**：每条配方卡必须包含「怎么做 / 花多少时间 / 风险 / 实测证据」，
   并给一个默认推荐项（带「推荐」标记 + 一句话理由），用户可以直接点「按推荐来」。
3. **做成软件**：见下一节。
4. **复用本地已装环境**（2026-11-05 追加）：不要求用户重装 RVC / UVR。
   `cover link` 自动探测或手动指定本机的 RVC 目录、RVC 解释器、`uvr_sep.py`、UVR 解释器，
   写进配置后 `cover sing` 直接调用本机这套程序；没有本地部署的人再走 pip 版依赖。
   默认后端因此从 `uvr` / `rvc` 改成 `local_uvr` / `local_rvc`。

## 十一、软件化方案（能不能做成一款软件）

能。但不是「PyInstaller 打一个 exe」那么简单，关键是**体积**和**首次启动**。

### 11.1 体积账（必须提前算）

| 组成 | 大小 |
|---|---|
| Python 运行时 | 60~90 MB |
| torch（CPU 版） | ~200 MB |
| torch（CUDA 12.x 版） | ~2.5 GB |
| UVR / 分离模型 | 300 MB ~ 1.5 GB |
| RVC 推理代码 + 依赖 | ~200 MB |
| 界面壳（Tauri） | ~10 MB |
| 界面壳（Electron） | ~150 MB |

结论：**CPU 版约 600 MB，CUDA 版 4~6 GB**。所以不能做成一个死包，必须分档下载。

### 11.2 推荐架构

```
安装包（Inno Setup，约 120MB）
  └─ 启动器（Tauri 壳 + 内置 Python 运行时）
       ├─ 首次启动向导：体检 → 选方案 → 按需下载依赖与模型（分档）
       └─ 本地后端 FastAPI（127.0.0.1 随机端口）+ 前端页面
```

- **壳**：Tauri（Rust + 系统 WebView），比 Electron 小一个数量级，Windows 10/11 自带 WebView2
- **后端**：内置 Python 3.11 embeddable + 预置 venv，不进系统 PATH，卸载即干净
- **依赖**：不预装 torch，首次启动按体检结果下载对应版本（CPU / CUDA 12.1 / CUDA 11.8）
- **模型**：与代码分离，走对象存储或 GitHub Release，带校验和；支持断点续传
- **更新**：代码增量更新（Tauri updater），模型单独版本号，不重复下载

### 11.3 分阶段落地

| 阶段 | 形态 | 用户拿到的东西 |
|---|---|---|
| v1（先做） | 绿色版目录 + `启动.bat` | 双击启动，浏览器自动打开界面，无需装 Python |
| v2 | 安装包（Inno Setup） | 开始菜单图标，首次启动向导 |
| v3 | Tauri 桌面应用 | 独立窗口、托盘、开机自启、后台队列 |

先做 v1 的原因：**打包不是难点，依赖下载才是**。v1 能最快验证「小白能不能一次装成」，
把下载器、校验、断点续传、失败回滚这些做完，v2/v3 只是套壳。

### 11.4 软件化带来的额外要求

- **单实例锁**：不能开两个界面抢同一块 GPU
- **后台常驻**：训练要跑 50 分钟，关窗口不能停（托盘 + 子进程守护）
- **崩溃恢复**：任务中断后能从 `work/<歌>/` 的状态文件续跑
- **日志**：一键导出诊断包（脱敏，不含路径和密钥）
- **权限**：不请求管理员权限；所有写入都在用户目录或安装目录

### 11.5 不做的

- 不做在线服务（GPU 成本不可控）
- 不做账号系统
- 不做云同步（曲库留在本地）
